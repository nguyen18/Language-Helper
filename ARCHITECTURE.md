# Language Helper — Architecture & Context

Deep-dive reference for future sessions/agents working on this repo. Read this before making changes so you don't have to re-derive context from scratch. Product ideas and planning live in `NOTES.md`; this doc covers the code and the reasoning behind it.

## What this project is

A language-learning app that teaches a new language by building on how the person already expresses themselves in their primary language. Instead of textbook vocabulary, the app finds the words and phrases the user actually uses (fillers, reactions, linking words, the way they show feelings) and teaches natural equivalents of *those* in the target language.

The long-term plan (see `NOTES.md`) is a personal phrasebook, a feelings map, practice using the user's own stories, flashcards and a coverage score, all built from one shared **phrase entry** data structure.

**What exists today is a proof of concept for one piece only, the Personal Word List Discoverer** (the owner's name for it, 2026-09-27; use this name when referring to the feature): the user has a casual chat with a scripted friend ("Mai", called "Sam" until 2026-09-26), and the app shows the user's top 100 most-used words. Since 2026-09-27 it lives on its own page, reached from a home page that shows Mai's study plan (a to-do list) and a site menu. A **Cheatsheet** page (2026-09-27) shows reference word lists, starting with the 100 most common words. Since 2026-10-01 the Cheatsheet's main list is the **user's own words** (from the Discoverer, typed or pasted, or an uploaded file), and a small **Supabase backend** translates words the pre-built files don't have (see "Backend"). Otherwise everything runs client-side: no accounts, no Claude calls yet. Replies never leave the device, except that dictation audio goes to the browser vendor's speech service (see "Dictation" below).

### Backend (`supabase/`, 2026-10-01)
Owner's request: build the "100 most common words you use" list from the Discoverer or from words the user types or uploads. Any word then needs translating, and which-dialect in the browser was measured at ~100 s and 9.5 MB for 3 words (cold CDN files take ~1 s each and a word needs dozens in a row), so the owner chose **"Backend now"** over a bigger pre-built bank or in-browser translation.
- **`translate` edge function** (Deno): `POST { target: 'vi-Southern' | 'vi-Central' | 'vi-Northern', words: string[] (≤ 25, ≤ 60 chars) }` → `{ entries }` in the same shape as the pre-built files. It reads cached rows from `public.translations` (`target, word, version, entry jsonb`; RLS on, no policies, so only the function's service role touches it), translates the rest with `makeEntry` (4 at a time) and upserts them, so **each word is translated once per language for everyone**. Lowercase words with no result are retried capitalized ("sunday" → *Chủ nhật*). Auth: the publishable key (`withSupabase({ auth: ['publishable', 'secret'] })`); CORS added around it.
- **Data from Storage, not the CDN:** the function's translator reads which-dialect's data from the public bucket `which-dialect` (`<version>/<lang>/…`), filled by `npm run mirror-data` (from the published npm packages; ~12k files, ~150 MB; skips existing files). Locally: 10 new words in ~0.5 s, cached words ~0.01 s.
- **Versions are pinned to 0.1.1** in three places that must move together: `supabase/functions/translate/deno.json` + `VERSION` in the function (cache rows are per version), `DATA_VERSION` in `mirror-data.ts`, and the package in `web/package.json` used by `npm run cheatsheet`. (The owner's which-dialect session published 0.2.0 / vi 0.1.2 the same day; upgrading is a separate step: bump all, mirror, regenerate. Building with `WHICH_DIALECT_DATA` uses the local checkout, which may be newer than the pinned version.)
- **Local dev:** Docker running, then from the repo root `npx supabase@2.119.0 start` (prints the URL and keys; serves the function), then `cd web && npm run mirror-data`, and put `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` in `web/.env.local` (see `web/.env.example`; restart `npm run dev` after changing it). The Supabase CLI runs through `npx` because Homebrew refused to install anything until Xcode is updated. After editing `functions/_shared`, restart the function (`docker restart supabase_edge_runtime_Language-Helper`); a running function doesn't reload it.
- **Not deployed yet:** hosting needs the owner's Supabase account: `npx supabase login`, `link --project-ref …`, `db push`, `functions deploy translate`, then `SUPABASE_URL=… SUPABASE_SECRET_KEY=… npm run mirror-data`, and the hosted URL and publishable key in the web app's env. Without the env vars the app still works for pre-built words; others show "not translated".
- **Not handled yet:** rate limiting (anyone with the publishable key can request translations; fine while the cache keeps cost low), accounts (the user's words stay in localStorage), clearing old-version cache rows.

## Architecture of `web/`

### Pages and routing (`App.tsx`, `lib/useRoute.ts`)
Four pages, chosen by the URL hash so refresh and the browser's Back button work without a router library or server config:

| Route | Hash | Page |
|---|---|---|
| `home` | `#/` (or no hash, or anything unknown) | `Home` |
| `discover` | `#/discover` | `Discoverer` |
| `cheatsheet` | `#/cheatsheet` | `Cheatsheet` |
| `settings` | `#/settings` | `Settings` |

`useRoute` reads `window.location.hash` and listens for `hashchange`; navigation is plain `<a href={ROUTE_HREF[...]}>` links. To add a page: add it to `Route` and `ROUTE_HREF` (`readRoute` looks the hash up in `ROUTE_HREF`), then to the switch in `App` and to `MENU_ITEMS`. If routes start needing parameters or nesting, that's the point to switch to a real router.

**Scroll:** `App` scrolls to the top when entering any page except the Discoverer. It deliberately doesn't for the Discoverer, whose own effect scrolls to the latest message (child effects run before the parent's, so a parent scroll-to-top would override it).

**Site header** (`SiteHeader` in `App.tsx`): a "✦ Language Helper ✦" brand link to home (styled after the Try Studio wordmark) and a **☰ Menu** button that opens a dropdown `<nav>` with links to Home, Cheatsheet and Settings (current page marked `aria-current="page"`; **the Discoverer is not in the menu** since 2026-10-01, owner's request: its way in is a slim "Find your words by chatting with Mai: Personal Word List Discoverer →" link at the bottom of the "100 most common words you use" card, in `MyWordsControls`, whose controls are compact once the list has words: box + Add + Upload on one row, "N of 100 words · Clear list" under it; **a full list (100) hides the box and Add** (owner's request), showing "Your list is full. Remove a word (✕) to add another." next to the upload button, which stays because a file can replace the list. The upload button is a smaller one labeled **"Upload your list of words"** (owner's feedback; was "Upload a file") (owner's feedback: the section took too much space; 233 → 125 px), plus the Home card and study-plan links) plus a greyed-out "Coming soon" list (Personal phrasebook, Feelings map, Flashcards, from `NOTES.md`). The menu closes on Escape, a click outside, or clicking a link. `SiteHeader` is rendered with `key={route}` so it remounts closed on every page change, including Back; this replaced a `setOpen(false)` effect that oxlint's `set-state-in-effect` rule flagged.

### Settings page and the target language (`pages/Settings.tsx`, `lib/languages.ts`) (2026-10-01)
Owner's request: "select which language we want to learn and this will be the language we translate words to for the whole website". `TARGET_LANGUAGES` lists what the site can translate English into: only what which-dialect supports, so for now **Vietnamese's three dialects** (`vi-Southern` default, `vi-Central`, `vi-Northern`; which-dialect has only vi and en, Spanish was removed). Each entry has `{ id, code, region, language, dialect, label }`; Settings groups dialects under their language as radio pills. The choice is saved in `localStorage` (`language-helper:target-language`) and read with `useTargetLanguage()` (`useSyncExternalStore`, updated by a same-tab custom event and the cross-tab `storage` event; an in-memory fallback if storage is unavailable). **Where it applies:** the Cheatsheet's built-in list (its own data file per language, see Generation) and its legend and header ("Translating to … · Change language"), and **new custom lists**, which save the language they were made in (`CustomList.target`; older lists have none and are Southern) and keep it if the setting changes. Home and the Discoverer show no translations yet. **Picks per language:** the built-in list's id (which keys picks) is `top-100` for Southern (unchanged, so earlier picks still apply) and `top-100:<id>` for the others. **Adding a language:** add it to `TARGET_LANGUAGES` once which-dialect supports it, then `npm run cheatsheet -- <id>`; it gets a pronoun table only if the package has one for it. Tested in Chrome: the Settings menu item, choosing Northern and then Central (live, without a reload) loads that language's file and shows its words (Central "what" → *chi*, Northern friend "you" → *cậu*).

### Cheatsheet page (`pages/Cheatsheet.tsx`, `lib/cheatsheet.ts`)

**Your words (2026-10-01; owner's request: the list is "built from the conversation with mai" or the user "can upload their 100 most common words by either writing it in english and adding it to the list or uploading a txt file or doc"):** the "100 most common words you use" list shows `useMyWords()` (up to 100, `localStorage` `language-helper:my-words`; starts empty, with an intro naming the three ways). **From the Discoverer:** its results screen has **"Use my words on the Cheatsheet"**, which saves only the words from the user's replies (not the "suggested" fill-ins) and opens the Cheatsheet. **Typed or pasted:** one box (Enter adds, Shift+Enter new line); up to 5 words on one line are added straight away (duplicates skipped, case-insensitively), anything bigger goes through the replace-or-add choice. **Uploaded:** .txt/.md as text, .docx by unzipping `word/document.xml` with fflate (paragraphs → lines); old .doc and PDF get a "save it as .docx or .txt" message. **`wordsFromText`:** if every item (split on lines, commas, semicolons, tabs) is a short list item (≤ 3 words, optionally numbered), it's a **list** and keeps its order and phrases ("going to"); otherwise the text is **counted** like the Discoverer and its most common words are used, ties in first-appearance order. When the list already has words, found words show as "Found N words in …" with **Replace my list / Add to my list / Cancel**. Each word has ✕; "Clear list" asks inline. **Translations:** `loadBank(target)` (the pre-built file: the owner's original 100 words + the pronoun table) first, then `useWordEntries` asks the backend for the rest in chunks of 25 (two requests at a time), showing "translating…" per row and a retry if it fails. The owner's original list is saved at `~/dev/my-top-100-words.txt` (one word per line) and uploading it restores the old list exactly. The list id (and so the user's picks) is unchanged. Tested in Chrome with the local backend: the empty state, uploading that file (100 words, all from the bank, in order), removing and typing words (translated by the backend in ~1 s), a .docx of prose (29 counted words, replaced, translated in 1.6 s), and the Discoverer button (mom → *má*, pho → *phở*).

**Since 2026-09-27 the built-in list is generated by [which-dialect](https://github.com/nguyen18/which-dialect)** (the owner's open-source any-language/any-dialect translator in `~/dev/which-dialect`), at the owner's request ("use our package for the translations and everything"). This **replaced** the hand-written Southern Vietnamese translations, alternatives (tui/tôi/mình…, bạn/mày/anh·chị, dạ/ừ, hông/không, kiểu/thích), usage notes, example sentences and the "why no direct translation" note for *the*, which the agent had written earlier that day. The package's results are weaker for grammar words (*the*, *I'll* and *going to* have no translation; some first translations are poor), which the owner accepted.

**Word list (`lib/topWords.ts`):** the owner's ranked `~/dev/top_100_words.txt`, with texting shorthand **replaced by the dictionary word in the same position** (owner's request 2026-09-27): im → I'm, ok → okay, thats → that's, dont → don't, ill → I'll, didnt → didn't, tho → though, gonna → going to, wanna → want to, kinda → kind of, its → it's. "i" is written "I" (the dictionary stores the pronoun capitalized). Keep the order. **Contractions stay** (I'm, that's, don't, I'll, didn't, it's): on 2026-09-27 they were removed and replaced with *as, he, by, an, his, has* (the most common English words not in the list, from wordfreq), then **restored on 2026-09-29** at the owner's request, after weighing splitting them into their parts (which would only have added *am*; the other parts are already in the list) against keeping them: they're how people actually talk, and they translate as units (*don't* → *đừng*). Weak spots: *I'll* has no translation, *I'm* only offers pronouns (Vietnamese usually drops "am"), *didn't* → slangy *cóc*. **Contraction parts (built 2026-09-29):** the build script splits each contraction (`contractionParts()`: *n't* → not, *'ll* → will, *'m* → am, *'re* → are, *'ve* → have, *'d* → would, *'s* → is, plus won't/can't/shan't/ain't/let's) and translates each part with a sense hint (`PART_HINTS`: *am/is/are* = "identical equivalent", *will* = "future tense", *not* = adverb, *that* = demonstrative determiner; anything else is a pronoun, translated with `register: 'casual'` and 6 options). English *do/does/did* in *don't/didn't* are `helper` parts (no word needed in Vietnamese or Spanish). Output: `parts: [{ word, helper?, options }]` per contraction. In the UI, `Row` joins each non-helper part's pick (or first option) into a **combined translation**, which `TranslationCell` puts **first** among the options (its gloss says "I + will, from its parts"); the box shows "I'll = I + will" and each part's options as star rows. Part picks are keyed by **part word** (`partKey(list, part)` → `part|list|i`), so starring *tui* for "I" changes both *I'm* (*tui là*) and *I'll* (*tui sẽ*). Defaults 2026-09-29: it's → *nó là*, that's → *đó là*, don't/didn't → *không*, I'm/I'll → *con là/con sẽ* (the package ranks *con* first for "I"; *tui* is 3rd with the casual register). This needed which-dialect fixes: *will* → *sẽ* (grammar phrases like "future tense"), nested *be* senses (copula → *là*), and the `register` option.

**Generation (`web/scripts/build-cheatsheet.ts`, `npm run cheatsheet`, or `npm run cheatsheet -- vi-Northern` for some languages):** for each language in `TARGET_LANGUAGES` and each word, `createTranslator().translate(word, { from: 'en', to: target.code, toRegion: target.region, limit: 5, allSenses: true })`, loading the package's data from the **jsDelivr CDN** (the published `which-dialect-<lang>` packages); set `WHICH_DIALECT_DATA=<path to which-dialect/packages>` to use a local checkout instead. From the CDN a full run takes ~4–5 minutes (every lookup is a download). `allSenses` keeps **every** English meaning, including ones with no translation (owner: "don't end it at 6 items"). Output `public/cheatsheet/top-100.<id>.json` per language (minified; was `top-100.json` before 2026-10-01; all three regenerated then from which-dialect 0.1.1 local data, ~1.4 MB each, 98/100 words translated, 57 of 100 words differ between Southern and Northern): per word, `meanings[]` of `{ id, pos, posName, gloss, via?, labels?, example?, translations[] }`, each translation `{ text, gloss, regions?, labels?, example?: { text, translation } }`. Meaning ids are `pos:slug-of-gloss` (up to 80 characters, with -2, -3… appended if two meanings of a word still collide) so picks survive regenerating. A 40-character slug collided for *I* ("The speaker or writer, referred to as the grammatical subject/object"), which showed two starred defaults. Latest run (2026-09-29, contractions restored): 98/100 words have a translation (*going to* and *I'll* have none); about 7 meanings per word on average, up to 25 (*going*). **Rerun after changing the word list or updating the package's data**, and commit the JSON.

**Loading:** the JSON is a static file (not bundled) that `loadTop100(target)` fetches once per language (memoized in a Map by language id; a failure clears that entry so it can retry). `Cheatsheet` calls React 19 `use(loadTop100(target))` with the Settings language, so switching languages suspends once while the other file loads; `App.tsx` lazy-loads the page (`React.lazy`) inside `ErrorBoundary` + `Suspense` ("Loading the cheatsheet…").

**Rows (`Row`):** rank · English word (`WordCell`) · translation (`TranslationCell`) · ✕ for custom lists. The **default meaning is the first one with a translation**; the picked meaning comes from `picks[meaningKey(list, word)]` (falls back to the default if the id no longer exists).
- **`WordCell`** (English word): a `Popover` button showing the word plus a small italic part-of-speech tag (`POS_ABBR`: *adj.*, *v.*, *pron.*, …). Its box lists every meaning as a star row: part of speech, definition, usage labels, the English example in quotes, "No translation found" when empty, and a "default" tag. Picking the default clears the saved pick.
- **`TranslationCell`**: shows the picked translation for the chosen meaning (`picks[optionKey(list, word, meaningId)]`, default = first) and "+N". Its box shows the chosen meaning (part of speech + definition), the translation options as star rows (text, its English gloss as the usage note, region badge when tagged, labels), and the picked option's example (Vietnamese text, then English). With no translation it shows "—" and a note suggesting another meaning. Words missing from the dictionary entirely (*going to*) show a plain "—".
- A hint under the legend explains both boxes; the card ends with the **required attribution**: "Meanings and translations from Wiktionary (CC BY-SA 4.0), via which-dialect." Keep it whenever this data is shown.
- Grid columns are at least 240px (two columns in the 680px layout) so word + tag and translation + "+N" each stay on one line (`white-space: nowrap` on the triggers).

**Pronoun table (2026-09-30; from which-dialect since its pronoun fix was published the same day):** Vietnamese pronouns depend on the relationship and come in pairs, so the pronoun words show a **"who are you talking to (or about)?" table** instead of a ranked list. The build script writes `pronounTable` from `createDictionary({ lang: 'vi' }).pronouns({ region: 'Southern' })`: 12 rows (`general` = neutral default, `friend`, `close-friend` ⚠ rude otherwise, `older-male`, `older-female`, `younger`, `parent`, `parents-age`, `grandparents-age`, `teacher`, `partner`, `formal`), each with six columns (`self` I, `addressee` you, `third` he/she, `selfPlural` we, `addresseePlural` plural you, `thirdPlural` they); each cell word keeps `speaker` (only if you're a man/woman), `gender` (he vs she) and `inclusive` (we incl./excl. the listener). The earlier hand-written `DRAFT_PRONOUN_TABLE` was removed. **Each word in a cell is on its own line** (`.pronoun-word` is `display: block`, no " / " separators; owner's request 2026-09-30), so cells with several choices ("we": chúng tôi, chúng ta, chúng mình, tụi tui) grow taller instead of wider. That made the "we" box shorter, 701px → 584px at 1436px wide, because the words no longer wrap mid-list.
- **Words (`pronounRole`):** I/me → `self`, my → "của" + self; you → `addressee`, your → "của" + addressee; we/us → `selfPlural`, our; he/him/his and she/her → `third` with gender; they/them/their → `thirdPlural`. Listener words (I, you, we…) use the **who you're talking to** pick; he/she/they use a separate **who you're talking about** pick (like the package's `listener`/`about`). **Talking-to tables show one column** (owner's request 2026-09-30): I/me/my/I'm/I'll → *Talking to* + "I"; you/your → *Talking to* + "you"; we → *Talking to* + "we". **Talking-about tables** (she/her/him/they/them) show "he/she" and "they" together, the looked-at one highlighted (`COLUMN_GROUPS`).
- **Picks (shared per list):** `pronounKey(list, 'listener' | 'about' | 'speaker')`. Defaults: listener = `friend` (Language Helper is casual chat; the package's own default is the neutral `general`), about = the package default (`general`). An **"I'm a man / a woman" toggle** appears when a shown cell depends on the speaker (someone younger: *anh*/*chị*; partner); without it both show, tagged "if you're a man/woman".
- **Empty cells** (e.g. "they" about grandparents) fall back to the default row's word (`pronounTextOrDefault`: *họ*), never to the dictionary's first translation (*tụi nó* is rude about elders).
- Contractions with a pronoun part (*I'm*, *I'll*) use the table for that part, and their box shows the table in place of the part's options.
- Tested 2026-09-30 in Chrome: defaults (I/me → mình, my → của mình, you → bạn, we → chúng mình, she/her → chỉ, him → ảnh, they/them → họ, I'll → mình sẽ); talking about grandparents' age → him ổng, she/her bả, they họ; someone younger + woman → I chị, I'll chị sẽ, you em; + man → anh, anh sẽ.

### Discoverer screens and state (`pages/Discoverer.tsx`)
Two views inside the page, switched by a `view` state (`'chat' | 'results'`). Both show a "Personal Word List Discoverer" eyebrow above the heading. The view isn't in the URL, so leaving the page and coming back always opens the chat (with the conversation intact).

**App state** is a single `SavedState` object:

| Field | Meaning |
|---|---|
| `replies: string[]` | The user's sent replies. `replies[i]` answers `MAI_SCRIPT[i]`. |
| `draft: string` | The current unsent text in the reply box. |

It's loaded from and saved to `localStorage` under the key `language-helper:chat` on every change, so a refresh doesn't lose the conversation. Both reads and writes are wrapped in `try/catch`; storage is a convenience and the app works without it. **Start over** confirms with `window.confirm`, then resets to `EMPTY_STATE`.

**Chat screen** (`Discoverer`):
- Renders `MAI_SCRIPT.slice(0, replies.length + 1)`: every Mai line already answered, plus the next line waiting for an answer. Each line is a `.turn` containing Mai's bubble and, if present, the user's reply bubble.
- There is no separate message list. The conversation is fully derived from `replies.length` and the script, which is why Mai's lines can't depend on what the user said.
- `finished` is `replies.length >= QUESTION_COUNT`. When true, the reply box is replaced by a **See my top 100 words** button. Mai's final line (the goodbye) is shown but never answered.
- Reply box: `<textarea>` with `autoCorrect="off"`, `autoCapitalize="off"`, `spellCheck={false}` so slang and fillers aren't "fixed". Enter sends, Shift+Enter adds a newline, and `isComposing` is checked so Enter during IME composition (e.g. typing Japanese) doesn't send.
- **+ um / + uh chips** (`insertFiller`) insert `"um, "` / `"uh, "` at the cursor (replacing any selection), adding a leading space if needed, then restore focus and cursor position on the next animation frame.
- **End chat and see my top 100 words** link appears once there's at least one reply, so users can stop early.
- Auto-scrolls to the bottom (`bottomRef`) whenever a reply is added or the view changes.

**Results screen** (`Results`):
- `topWords(replies, 100)` produces the list. Also shows reply count and total words (via `tokenize`).
- Real words show a bar scaled to the top count. Suggested (fallback) words are greyed out with a "suggested" label and no count.
- If any fallback words were used, a line explains how many came from the user's replies.

### Mai's script (`conversation.ts`)
`MAI_SCRIPT` is a fixed array of 14 lines. The first 13 each expect a reply; the last is a goodbye (`QUESTION_COUNT = MAI_SCRIPT.length - 1`). The lines cover the same ground as the original prompt list: the week, something annoying, something exciting, a recommendation, a funny/embarrassing story, and stress. Each Mai line opens with a generic reaction ("Ugh, I'd be annoyed too", "No way!") so it fits whatever the user said, then asks an open question that invites storytelling, which is where fillers and reactions show up.

Editing the script is safe: the UI and counts derive from its length. Keep the last line a closing line with no question, or change the `QUESTION_COUNT` logic.

### Word counting (`wordCounts.ts`)
- `tokenize(text)` — converts curly apostrophes (`‘ ’`) to `'`, lowercases, then matches `/[\p{L}\p{N}]+(?:'[\p{L}\p{N}]+)*/gu`: runs of letters/digits, with inner apostrophes allowed so "don't" and "I'm" stay single words. Unicode-aware, so accented letters work. Hyphenated words split ("kinda-sorta" → two words), and numbers count as words.
- `topWords(texts, limit = 100)` — counts every token across all replies (**every word counts**: nouns, fillers and common words included), sorts by count descending then alphabetically, and takes the first `limit`. If that's fewer than `limit`, it tops up from `FALLBACK_WORDS` in list order, skipping any word already present, marking these `suggested: true` with `count: 0`.
- `FALLBACK_WORDS` — a fixed list of 100 everyday words **supplied by the project owner**. Keep it exactly as given (order and contents), including its few nouns (Person, Friend, Time, …); changes to it should come from the owner. It's also recorded verbatim in `NOTES.md`.
- `displayWord(word)` — words are stored lowercase; this capitalizes "i" and "i'm"/"i've"/etc. for display.

### Dictation (`useDictation.ts`)
The notes originally planned to rely on the phone keyboard's built-in dictation (no in-app button). Desktop browsers don't have that, so a **🎤 Dictate** button was added using the Web Speech API (`SpeechRecognition` / `webkitSpeechRecognition`).

- Supported in Chrome, Edge and Safari; not Firefox. `dictationSupported` is checked once at load; unsupported browsers see a note suggesting another browser or OS dictation (on a Mac, press Fn twice).
- Minimal Web Speech API types are declared in the file because not every TypeScript `lib.dom` includes them.
- Settings: `continuous = true`, `interimResults = true`, `lang = navigator.language`.
- In-progress speech is exposed as `interim` (shown in grey italics above the reply box). Each finished phrase is passed to `onFinal`, which the app **appends to the end of the draft**, not at the cursor.
- `onFinal` is kept in a ref updated in an effect (not during render; oxlint's `react(refs)` rule flags that).
- Errors: `not-allowed` → "Microphone access was blocked."; `no-speech` and `aborted` are ignored; others are shown.
- Dictation stops when the user sends a reply, when the view changes, and on unmount, so speech never lands somewhere unexpected.
- **Privacy caveat:** Chrome sends the audio to Google's servers for recognition (free, but not on-device). Safari uses Apple's service.
- Browser recognition, like keyboard dictation, usually drops "um"/"uh", which is why the filler chips remain.

## If this grows

- **Phrases, not just words**: the product is built around phrases (`NOTES.md`'s phrase entry: phrase → purpose → feeling → equivalents by formality → examples). Counting two- and three-word phrases ("you know", "I mean") is the obvious next step from word counts, and designing the phrase entry data model is an open to-do.
- **Backend**: when replies need to reach Claude (for Mai's replies, tagging purpose/emotion, or target-language equivalents), add Supabase serverless functions as planned rather than calling the API from the browser. Cache equivalents per phrase, and use the Batch API (50% off) where results don't need to be instant.
- **Routing**: the hash router in `useRoute.ts` is fine for a handful of flat pages. Switch to a real router when routes need parameters or nesting.
- **Mobile**: before wrapping in Capacitor, test dictation there. The Web Speech API behaves differently in iOS WebViews, and the original plan (keyboard dictation, no button) may be the better path on phones.

## Working conventions for this repo

- TypeScript everywhere, per the planned stack.
- **Record product decisions in `NOTES.md`** (the owner asks for this) and code-level details here. When a decision is reversed, say so in both, rather than silently deleting the old one.
- Every word counts in the top 100. Don't add filtering (nouns, stopwords) without the owner asking.
