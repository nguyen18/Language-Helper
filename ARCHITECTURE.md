# Mai (mai-tutor) — Architecture & Context

Deep-dive reference for future sessions/agents working on this repo. Read this before making changes so you don't have to re-derive context from scratch. Product ideas and planning live in `NOTES.md`; this doc covers the code and the reasoning behind it.

## What this project is

A language-learning app that teaches a new language by building on how the person already expresses themselves in their primary language. Instead of textbook vocabulary, the app finds the words and phrases the user actually uses (fillers, reactions, linking words, the way they show feelings) and teaches natural equivalents of *those* in the target language.

The long-term plan (see `NOTES.md`) is a personal phrasebook, a feelings map, practice using the user's own stories, flashcards and a coverage score, all built from one shared **phrase entry** data structure.

**What exists today is a proof of concept for one piece only, the Personal Word List Discoverer** (the owner's name for it, 2026-09-27; use this name when referring to the feature): the user has a casual chat with a scripted friend ("Mai", called "Sam" until 2026-09-26), and the app shows the user's top 100 most-used words. Since 2026-09-27 it lives on its own page, reached from a home page that shows Mai's study plan (a to-do list) and a site menu. A **Cheatsheet** page (2026-09-27) shows reference word lists, starting with the 100 most common words. Since 2026-10-01 the Cheatsheet's main list is the **user's own words** (from the Discoverer, typed or pasted, or an uploaded file), and a small **Supabase backend** translates words the pre-built files don't have (see "Backend"). A **Journal** page (2026-10-01) holds entries written in the target language, with photos, cut-out stickers and an audio note, corrected by the backend's `check-spelling` function (which-dialect 0.4.0's journal review: a spellchecker plus English-to-Vietnamese, with optional regional and pronoun checks) and a sentence-frames browser. Otherwise everything runs client-side: no accounts, no Claude calls yet. Replies never leave the device, except that dictation audio goes to the browser vendor's speech service (see "Dictation" below).

### Backend (`supabase/`, 2026-10-01)
Owner's request: build the "100 most common words you use" list from the Discoverer or from words the user types or uploads. Any word then needs translating, and which-dialect in the browser was measured at ~100 s and 9.5 MB for 3 words (cold CDN files take ~1 s each and a word needs dozens in a row), so the owner chose **"Backend now"** over a bigger pre-built bank or in-browser translation.
- **`translate` edge function** (Deno): `POST { target: 'vi-Southern' | 'vi-Central' | 'vi-Northern', words: string[] (≤ 25, ≤ 60 chars) }` → `{ entries }` in the same shape as the pre-built files. It reads cached rows from `public.translations` (`target, word, version, entry jsonb`; RLS on, no policies, so only the function's service role touches it), translates the rest with `makeEntry` (4 at a time) and upserts them, so **each word is translated once per language for everyone**. Lowercase words with no result are retried capitalized ("sunday" → *Chủ nhật*). Auth: the publishable key (`withSupabase({ auth: ['publishable', 'secret'] })`); CORS added around it.
- **Data from Storage, not the CDN:** every function reads which-dialect's data from the public bucket `which-dialect`, one folder per language and **data package version** (`en@0.1.1`, `vi@0.1.4`; `_shared/data.ts`'s `dataUrl` and `DATA_VERSIONS`), filled by `npm run mirror-data` (`DATA_SETS`, from the published npm packages; ~12k files, ~150 MB; skips existing files). Before the 0.5.0 bump, folders were named after the which-dialect version (`0.1.1/en`, `0.4.0/vi`, …); those are unused and can be deleted. Locally: 10 new words in ~0.5 s, cached words ~0.01 s.
- **`check-spelling` edge function** (2026-10-01, for the Journal; named `check-grammar` until the owner renamed it the same day, since which-dialect's checker became a spellchecker by default; the app's `checkGrammar`, `lib/grammar.ts` and `GrammarCheck` became `checkSpelling`, `lib/spelling.ts`, `SpellingCheck`): `POST { target, text (≤ 5000 chars), checks? }` → which-dialect's journal **`Review`** `{ text (NFC), corrected, sentences[] }` from `createReviewer().review(text, { lang, region, base: 'en', checks })`. **which-dialect 0.4.0** (owner's request 2026-10-01, implementing `JOURNAL_PLAN.md`): the review is a **spellchecker by default**: English words get the region's word (*market* → *chợ*, *ice cream* → *kem*) or are left out (*the*), missing accents are added (*Toi muon an* → *Tôi muốn ăn*, *khong* → *không*), and an English sentence or clause that follows a sentence frame gets the frame's wording (*but it was expensive* → *nhưng mắc quá*). `checks` turns on only the journal's two opt-in checks, `dialect` (*lợn* → *heo* in Southern) and `pronoun-consistency` (*tôi* earlier, *tui* later → *tôi*); other values are ignored. Each sentence has `original`, `corrected`, `changes` (`{ from, to, why, kind }`, `to` empty when a word is left out), `hints`, `frames` (`{ id, en, text }`, which frames the sentence follows; frames no longer change a sentence) and `unchecked` (English with no translation). It also adds each sentence's `words` (its words of several syllables, from `dictionary.segment`, as offsets into `corrected`), and runs `createChecker().check()` with the same rules to give each change `options`, the matching issue's suggestions (matched by rule and word, in order), when there's more than one, since the review keeps only the first. Each option is `{ text, meanings }`: up to 3 senses from `dictionary.lookup` (`{ pos, posName, gloss (≤ 2 definitions), regions? (only when tagged for some regions), labels? }`); English-word options come with no meanings, because the web side shows their Cheatsheet entry. No listener (a journal is written to yourself). Locally ~2.7 s cold, ~0.2–0.5 s warm.
- **`sentence-frames` edge function** (2026-10-01): `POST { target, topic? }` → `{ frames }`, which-dialect's `createPhrasebook().frames({ lang, region, topic })`: each frame's English and pattern for the region with slots open (Southern *{place} ở đâu?*, Central *{place} ở mô?*), its `topic` (journal, feelings, questions, requests, greetings) and `slots`. 34 frames in which-dialect so far.
- **`word-options` edge function** (2026-10-01): `POST { target, word }` → `{ word, accents, synonyms }`, each a `WordOption` (`{ text, meanings }`); the word can have several syllables: the word's own meanings; **the same letters with other accents** (which-dialect's `dictionary.variants`, since 0.5.0: dictionary words only, most common first, up to 5, for words of any length: *hom nay* → *hôm nay*; syllable languages only): a real word with the wrong tone (*muộn* for *muốn*) passes the spellchecker, and this is how the learner catches it; and **synonyms** from the word's first 3 senses (up to 6, often another region's word: *ngô* → *bắp*). ~0.02–0.5 s.
- **`_shared/words.ts`:** `describeWord` (a word's first 3 meanings: part of speech, ≤ 2 definitions, regions when tagged for some regions, labels), used by `check-spelling` and `word-options`; which-dialect is passed in, like `_shared/entries.ts`.
- **Shared by the journal functions** (`functions/_shared/journal.ts`): `TARGETS`, CORS (`withCors`), and `dataUrl` (re-exported from `_shared/data.ts`).
- **which-dialect 0.5.0 everywhere** (owner's request 2026-10-01, "let's just bump everything"): all four functions' `deno.json`, the type imports in `_shared/entries.ts` and `_shared/words.ts`, and `web/package.json` (used by `npm run cheatsheet`), with data en 0.1.1 and vi 0.1.4. To upgrade: bump those, `DATA_VERSIONS` in `_shared/data.ts` and `DATA_SETS` in `mirror-data.ts`, run `npm run mirror-data`, bump `VERSION` in `translate` (its cache rows are per version, so every word is translated again once), regenerate the Cheatsheet, and restart the functions. 0.5.0 brought `dictionary.segment` and `dictionary.variants` (the journal's words of several syllables) and the spellchecker's fixing of accents by neighboring syllables (*Hom nay* → *Hôm nay*, not *Hôm này*).

### Testing on a phone (noted 2026-10-01)
There's no native app yet (Capacitor is planned, below), so the phone test is the web app in the phone's browser.
- **Same Wi-Fi, plain http (what the owner uses for now):** from `web/`, `VITE_SUPABASE_URL=http://<Mac's IP>:54321 npm run dev -- --host --port 5199`, then open `http://<Mac's IP>:5199` on the phone (`ipconfig getifaddr en0` gives the IP; it was 192.168.1.113). The env override beats `.env.local` (whose `127.0.0.1` would mean the phone itself), so translations and journal checks work; local Supabase answers on the network address too.

The owner chose to ignore these for now (2026-10-01). Two fixes when needed: fall back to another id generator when `randomUUID` is missing (makes saving work over http), or use an https tunnel.
- **https tunnel (for testing everything):** a program on the Mac (e.g. Cloudflare's free quick tunnels: `npx cloudflared tunnel --url http://localhost:5199`, no account) gives a random `https://….trycloudflare.com` link that forwards to the Mac, so the phone gets a secure page and nothing is blocked, on any network. It needs **two** tunnels (the app and Supabase on 54321), with `VITE_SUPABASE_URL` set to the Supabase tunnel, because a secure page can't call a plain-http backend. Anyone with a link can reach the local app while the tunnels run; links are random and die when they stop. Run `cloudflared` via npx: Homebrew won't install anything until Xcode is updated.

## Architecture of `web/`

### Pages and routing (`App.tsx`, `lib/useRoute.ts`)
Five pages, chosen by the URL hash so refresh and the browser's Back button work without a router library or server config:

| Route | Hash | Page |
|---|---|---|
| `home` | `#/` (or no hash, or anything unknown) | `Home` |
| `discover` | `#/discover` | `Discoverer` |
| `cheatsheet` | `#/cheatsheet` | `Cheatsheet` |
| `journal` | `#/journal` | `Journal` (lazy-loaded, like the Cheatsheet) |
| `settings` | `#/settings` | `Settings` |

`useRoute` reads `window.location.hash` and listens for `hashchange`; navigation is plain `<a href={ROUTE_HREF[...]}>` links. To add a page: add it to `Route` and `ROUTE_HREF` (`readRoute` looks the hash up in `ROUTE_HREF`), then to the switch in `App` and to `MENU_ITEMS`. If routes start needing parameters or nesting, that's the point to switch to a real router.

**Scroll:** `App` scrolls to the top when entering any page except the Discoverer. It deliberately doesn't for the Discoverer, whose own effect scrolls to the latest message (child effects run before the parent's, so a parent scroll-to-top would override it).

**Site header** (`SiteHeader` in `App.tsx`): a "✦ Mai ✦" brand link to home (styled after the Try Studio wordmark) and a **☰ Menu** button that opens a dropdown `<nav>` with links to Home, Cheatsheet, Journal and Settings (current page marked `aria-current="page"`; **the Discoverer is not in the menu** since 2026-10-01, owner's request: its way in is a slim "Find your words by chatting with Mai: Personal Word List Discoverer →" link at the bottom of the "100 most common words you use" card, in `MyWordsControls`, whose controls are compact once the list has words: box + Add + Upload on one row, "N of 100 words · Clear list" under it; **a full list (100) hides the box and Add** (owner's request), showing "Your list is full. Remove a word (✕) to add another." next to the upload button, which stays because a file can replace the list. The upload button is a smaller one labeled **"Upload your list of words"** (owner's feedback; was "Upload a file") (owner's feedback: the section took too much space; 233 → 125 px), plus the Home card and study-plan links) plus a greyed-out "Coming soon" list (Personal phrasebook, Feelings map, Flashcards, from `NOTES.md`). The menu closes on Escape, a click outside, or clicking a link. `SiteHeader` is rendered with `key={route}` so it remounts closed on every page change, including Back; this replaced a `setOpen(false)` effect that oxlint's `set-state-in-effect` rule flagged.

### Settings page and the target language (`pages/Settings.tsx`, `lib/languages.ts`) (2026-10-01)
Owner's request: "select which language we want to learn and this will be the language we translate words to for the whole website". `TARGET_LANGUAGES` lists what the site can translate English into: only what which-dialect supports, so for now **Vietnamese's three dialects** (`vi-Southern` default, `vi-Central`, `vi-Northern`; which-dialect has only vi and en, Spanish was removed). Each entry has `{ id, code, region, language, dialect, label }`; Settings groups dialects under their language as radio pills. The choice is saved in `localStorage` (`mai-tutor:target-language`) and read with `useTargetLanguage()` (`useSyncExternalStore`, updated by a same-tab custom event and the cross-tab `storage` event; an in-memory fallback if storage is unavailable). **Where it applies:** the Cheatsheet's built-in list (its own data file per language, see Generation) and its legend and header ("Translating to … · Change language"), and **new custom lists**, which save the language they were made in (`CustomList.target`; older lists have none and are Southern) and keep it if the setting changes. Home and the Discoverer show no translations yet. **Picks per language:** the built-in list's id (which keys picks) is `top-100` for Southern (unchanged, so earlier picks still apply) and `top-100:<id>` for the others. **Adding a language:** add it to `TARGET_LANGUAGES` once which-dialect supports it, then `npm run cheatsheet -- <id>`; it gets a pronoun table only if the package has one for it. Tested in Chrome: the Settings menu item, choosing Northern and then Central (live, without a reload) loads that language's file and shows its words (Central "what" → *chi*, Northern friend "you" → *cậu*).

### Journal page (`pages/Journal.tsx`, `lib/journal.ts`, `lib/spelling.ts`) (2026-10-01)
Owner's request: journal entries (called the **diary** until the 2026-10-01 rename; the IndexedDB store moved from `diary-entries` to `journal-entries` in database version 2) written **in the target language** (English allowed for words the learner doesn't know yet, since `JOURNAL_PLAN.md`), on an entry sheet where a photo and/or stickers ("like those iPhone stickers made cutting out parts of photos") can go **anywhere**; a date and time per entry; an optional **audio note** (entries can be written or spoken, but if spoken the user is encouraged to type out what they said so it can be corrected); spell-checked with which-dialect's checker, the **original kept intact in blue and the corrected entry underneath in red**, using the site's existing hues; **latest entry on top** for now.
- **Storage:** IndexedDB database `mai-tutor` (named `language-helper` until 2026-10-07; `moveOldDb` copies an old one over on first open, then deletes it) (stores `journal-entries` and `stickers`), because photos, stickers and audio are Blobs, too big for `localStorage`. No accounts yet, so entries stay in that browser; the first save asks `navigator.storage.persist()` so the browser is less likely to clear them. If IndexedDB is unavailable (some private modes), the page says so.
- **Entry** (`JournalEntry`): `targetId` (the language when first saved; later Settings changes don't move old entries), `when` (a `datetime-local` value, default now), `text`, `items`, `audio?` (`{ blob, seconds }`), `check?` (the latest `SpellingCheck`, with the `input` it checked, so an edited entry is checked again only when its words changed), `createdAt`/`updatedAt`. Sorted by `when`, then `createdAt`, newest first.
- **Sheet** (`JournalSheet`): lined paper; the text is a textarea that grows with its content (a `<p>` when read). ### Word counting (`wordCounts.ts`)
- `tokenize(text)` — converts curly apostrophes (`‘ ’`) to `'`, lowercases, then matches `/[\p{L}\p{N}]+(?:'[\p{L}\p{N}]+)*/gu`: runs of letters/digits, with inner apostrophes allowed so "don't" and "I'm" stay single words. Unicode-aware, so accented letters work. Hyphenated words split ("kinda-sorta" → two words), and numbers count as words.
- `topWords(texts, limit = 100)` — counts every token across all replies (**every word counts**: nouns, fillers and common words included), sorts by count descending then alphabetically, and takes the first `limit`. If that's fewer than `limit`, it tops up from `FALLBACK_WORDS` in list order, skipping any word already present, marking these `suggested: true` with `count: 0`.
- `FALLBACK_WORDS` — a fixed list of 100 everyday words **supplied by the project owner**. Keep it exactly as given (order and contents), including its few nouns (Person, Friend, Time, …); changes to it should come from the owner. It's also recorded verbatim in `NOTES.md`.
- `displayWord(word)` — words are stored lowercase; this capitalizes "i" and "i'm"/"i've"/etc. for display.

### Dictation (`useDictation.ts`)
The notes originally planned to rely on the phone keyboard's built-in dictation (no in-app button). Desktop browsers don't have that, so a **🎤 Dictate** button was added using the Web Speech API (`SpeechRecognition` / `webkitSpeechRecognition`).

- Supported in Chrome, Edge and Safari; not Firefox. `dictationSupported` is checked once at load; unsupported browsers see a note suggesting another browser or OS dictation (on a Mac, press Fn twice).
- Minimal Web Speech API types are declared in the file because not every TypeScript `lib.dom` includes them.
- Settings: `continuous = true`, `interimResults = true`, `lang = navigator.language`.
- In-progress speech is exposed as `interim` (shown in grey italics above the reply box). Each finished phrase is passed to `onFinal`, which the app **appends to the end of the draft**, not at the cursor.
- `onFinal` is kept in a ref updated in an effect (not during render; oxlint's `react(refs)` rule flags that).
- Errors: `not-allowed` → "Microphone access was blocked."; `no-speech` and `aborted` are ignored; others are shown.
- Dictation stops when the user sends a reply, when the view changes, and on unmount, so speech never lands somewhere unexpected.
- **Privacy caveat:** Chrome sends the audio to Google's servers for recognition (free, but not on-device). Safari uses Apple's service.
- Browser recognition, like keyboard dictation, usually drops "um"/"uh", which is why the filler chips remain.

## Working conventions for this repo

Features are rule-based and data-driven, from which-dialect's data (dictionary, pronoun table, picks, sentence frames, checker), with no API costs or LLM dependency. Don't propose AI rewrite buttons, LLM fallbacks or "needs AI" paths; when rules can't handle something, say so and fall back to hints.
